
# Ghost Queue — Technical Workflow

## 1. Architecture Overview

Ghost Queue is a proposed modular workflow auditing system. Its architecture separates data validation, rule-based detection, AI-assisted explanation, prioritization, and human review.

### Proposed Technology Stack

- **Workflow orchestration:** n8n
- **Database:** Supabase / PostgreSQL
- **Detection logic:** JavaScript or SQL rules
- **AI explanation:** An LLM provider such as Gemini, subject to availability and data-protection requirements
- **Review interface:** A lightweight web dashboard or structured review interface

These technologies describe the proposed architecture. Mark each component as implemented only after verifying it in the repository or running prototype.

## 3. Input Schema

A minimal case record may contain:

| Field | Purpose |
|---|---|
| `case_id` | Unique, non-identifying case reference |
| `created_at` | Case creation timestamp |
| `last_activity_at` | Timestamp of the last meaningful activity |
| `status` | Current workflow status |
| `department_id` | Current responsible department |
| `handoff_count` | Number of recorded transfers |
| `missing_fields` | Known missing requirements |
| `due_at` | Applicable deadline, if defined |
| `case_type` | Workflow category for threshold selection |

Use synthetic or anonymized records during early development. Adapt the actual schema to available data and organizational requirements.

## 4. Processing Stages

### Stage 1: Ingestion

Receive records from an authorized source or load a sample dataset. Validate field types, timestamps, identifiers, and required fields.

Invalid records should be marked for correction rather than silently discarded.

### Stage 2: Rule-Based Detection

Apply configurable rules.

- **Stagnation:** Time since meaningful activity exceeds the threshold for the relevant case type.
- **Repeated handoffs:** Recorded transfers exceed a configured threshold without evidence of resolution.
- **Missing information:** One or more required fields remain incomplete for the current stage.

Thresholds should be determined from applicable service standards or validated historical data. They must not be presented as universal standards.

### Stage 3: Evidence Assembly

For each flagged case, assemble the specific facts that triggered the warning: relevant timestamps, transfer counts, missing fields, and the rules applied.

This evidence becomes the basis for the explanation.

### Stage 4: AI-Assisted Explanation

Where an AI service is available and appropriate, provide only the minimum necessary evidence and request a concise summary.

The model should:
- Summarize supplied facts without inventing details.
- Distinguish recorded facts from possible interpretations.
- State when information is insufficient.
- Suggest a review action rather than make an irreversible decision.

The deterministic detection result remains authoritative for measurable conditions.

### Stage 5: Priority Calculation

Apply a documented policy using factors such as deadline urgency, potential impact, duration of blockage, evidence confidence, and follow-up effort.

Do not allow an LLM to silently determine the score. Document weights and validate the resulting ranking with human reviewers.

### Stage 6: Human Review

An authorized reviewer should be able to:
- Inspect the supporting evidence.
- Confirm or dismiss the warning.
- Correct inaccurate information.
- Record the selected intervention and reason.
- Escalate cases according to approved procedures.

### Stage 7: Audit and Outcome Tracking

Store the rule results, evidence references, recommendation, reviewer decision, timestamps, and outcome where appropriate.

Use these records to evaluate false positives, missed cases, and whether interventions improve resolution.

## 5. Example Workflow Record

The following is a hypothetical illustration, not a real case or a measured result.

```json
{
  "case_id": "DEMO-001",
  "status": "pending",
  "days_since_last_activity": 18,
  "handoff_count": 4,
  "missing_fields": ["supporting_document"],
  "flags": [
    "stagnation_threshold_exceeded",
    "repeated_handoffs",
    "missing_information"
  ],
  "review_status": "awaiting_human_review"
}
```

In this example, the system identifies three review signals. It does not conclude that a person or department is at fault. A reviewer must check whether the delay is justified and what action is appropriate.

## 6. Testing Plan

1. Create labelled synthetic records covering normal, delayed, repeatedly transferred, and incomplete cases.
2. Test each detection rule independently.
3. Verify that every flag links to the correct evidence.
4. Check AI summaries for unsupported claims.
5. Measure precision, recall, and false-positive rates against reviewed labels.
6. Test missing, malformed, and contradictory data.
7. Verify access controls and audit logging.
8. Conduct a small authorized pilot before considering operational deployment.

## 7. Failure Handling and Security

- Handle unavailable AI services without losing rule-based results.
- Avoid sending unnecessary personal or confidential information to external models.
- Restrict database access using appropriate authentication and permissions.
- Log errors without exposing sensitive case details.
- Provide a manual review path when data or AI explanations are unreliable.
- Retain records only according to applicable policies.

## 9. Conclusion

Ghost Queue separates measurable workflow detection from AI-assisted explanation and human decision-making. This modular design makes the concept easier to test, audit, and improve.

Its success should be demonstrated through a working workflow, traceable evidence, realistic testing, and measured results—not through architecture diagrams or AI-generated explanations alone.
